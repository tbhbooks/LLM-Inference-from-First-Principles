==============================================================================
  PART 3: The Iteration-Level View
==============================================================================

  Let's zoom into iterations 2-4 to see what happens at each step.

  === Iteration 2 ===
  Before: batch = [R0, R1, R2, R3]
  Execute: all 4 generate one token
  After:
    R0: 2/3 tokens (Running)
    R1: 2/8 tokens (Running)
    R2: 2/2 tokens → FINISHED
    R3: 2/10 tokens (Running)
  Scheduler: R2 finished. Remove R2. Pull R4 from waiting queue.
  Next batch: [R0, R1, R4, R3]

  === Iteration 3 ===
  Before: batch = [R0, R1, R4, R3]
  Note: R4 is NEW — it needs prefill (processing prompt tokens)
  Execute: R0, R1, R3 decode; R4 prefills
  After:
    R0: 3/3 tokens → FINISHED
    R1: 3/8 tokens (Running)
    R4: prefill complete, 0/4 decode tokens
    R3: 3/10 tokens (Running)
  Scheduler: R0 finished. Remove R0. Pull R5 from waiting queue.
  Next batch: [R5, R1, R4, R3]

  === Iteration 4 ===
  Before: batch = [R5, R1, R4, R3]
  Note: R5 is NEW — needs prefill
  Execute: R1, R4, R3 decode; R5 prefills
  After:
    R5: prefill complete (Running)
    R1: 4/8 tokens (Running)
    R4: 1/4 tokens (Running)
    R3: 4/10 tokens (Running)

  Key insight: the scheduler makes decisions EVERY iteration.
  No waiting for the batch to drain. No idle GPU slots.

==============================================================================
  PART 4: Mixed Batches — Prefill Meets Decode
==============================================================================

  At iteration 3, the batch contains:

    Slot 0: R0 — decode (generating token 3/3)
    Slot 1: R1 — decode (generating token 3/8)
    Slot 2: R4 — PREFILL (processing 10 prompt tokens)
    Slot 3: R3 — decode (generating token 3/10)

  This is a mixed batch: 3 decode + 1 prefill.

  Prefill vs Decode work:
    Decode: process 1 token per sequence (cheap per sequence)
    Prefill: process ALL prompt tokens at once (expensive per sequence)

  The GPU handles both in the same iteration. But prefill uses
  more compute per sequence — the scheduler must account for this
  when deciding how many prefills to allow per iteration.

  This is why continuous batching needs a smart scheduler:
    - Too many prefills → decode requests starve (latency spikes)
    - Too few prefills → new requests wait too long (queue grows)
    - The right balance → high throughput AND low latency

  Chapter 12 builds this scheduler.

==============================================================================
  PART 5: The New Types — SequenceStatus and SequenceGroup
==============================================================================

  SequenceStatus enum:
    Waiting   — queued, not yet scheduled
    Running   — actively generating tokens
    Finished  — generation complete

  Lifecycle demo:

  [Create] Request "What is AI?" → tokens [2061, 318, 9552, 30]
    SequenceGroup { group_id: 1, status: Waiting }
      Sequence { seq_id: 1, prompt: [2061, 318, 9552, 30], output: [] }
      num_tokens() = 4
      is_prefill() = true

  [Schedule] Scheduler picks group 1 for processing
    SequenceGroup { group_id: 1, status: Running }
      Sequence { seq_id: 1, status: Running }

  [Prefill] Process all prompt tokens, generate first output token
    Sequence { seq_id: 1, prompt: [2061, 318, 9552, 30], output: [464] }
    num_tokens() = 5
    is_prefill() = false

  [Decode] Generate tokens one at a time...
    output: [464, 2159]          num_tokens() = 6
    output: [464, 2159, 286]     num_tokens() = 7
    output: [464, 2159, 286, 9552]  num_tokens() = 8

  [Finish] Stop token or max length reached
    SequenceGroup { group_id: 1, status: Finished }
      Sequence { seq_id: 1, status: Finished }

  Transitions: Waiting → Running → Finished (never backward)

==============================================================================
  PART 6: The Throughput Multiplier
==============================================================================

  Head-to-head comparison (8 requests, batch size 4):

  Metric                     Static      Continuous
  ─────────────────────────  ──────      ──────────
  Total iterations           17          15
  GPU idle slot-iterations   23          15
  Overall utilization        66.2%       75.0%
  Tokens generated           45          45
  Throughput (tok/iter)      2.65        3.00

  Continuous batching generates the same 45 tokens in fewer iterations,
  with fewer wasted GPU slots.

  At scale (100+ requests, high variance in output length):
    - Static batching: longest request in each batch dominates
    - Continuous batching: finished requests leave immediately
    - Throughput improvement: 2-3x is typical
    - Latency improvement: new requests start sooner (no waiting for batch)

  The more variance in output lengths, the bigger the win.
  The more requests in the queue, the fuller the batch stays.

  This is why every production inference engine uses continuous batching.
